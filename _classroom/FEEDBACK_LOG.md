## step1 — 為什麼要有 harness

**教學指示重點**：讀 `demo/PROMPT.md` 確認兩版需求只差「有沒有附規矩」；比對 `no-harness.html` 與 `with-harness.html`；填出三列對照表（顏色從哪來／業務規則從哪來／多出來的東西）。PM 另加三題（一句話向老闆解釋 harness、舉例「管不住做多少」、時間夠不夠）；QA 另加主作業：把手冊 Step 1 的 11 項事實主張逐條拿去跟實檔勾稽。

**實際成果抽查**：兩份回饋檔都產出。PM 自己填出的三列表用的是實檔證據（`--brand: #e8590c` vs `--ui-sys-color-primary: #C8232C`），沒有照抄手冊。QA 交出 11 列勾稽表，10 條成立、1 條部分成立。

### 講師觀察（step6）

1. **兩位對同一份成品給出 3/5 與 4.8/5，差距是全課最大的一次——而且兩個評分都對。** QA 評的是「流程有沒有貫通」（貫通了），PM 評的是「產品目標有沒有達成」（沒達成）。**教材把這題叫「做一個能上線的課程回饋問卷」，用的是 PM 的標準；但它交付的是 QA 標準下的成功。** 這個落差要修在文案，不是修在程式。
2. **`localStorage` 的資料孤島是這一題的結構性問題，兩位獨立抓到。** README 承諾「真的網址、傳給同事看」「admin 看全部回覆」，PRD 卻規定資料存在填答者自己的瀏覽器。**同事打開你的網址填完，你在自己的 admin 一筆也看不到。** 修法很便宜（把定位講清楚＋加一項無痕視窗的驗收），但不修的話，這一題會在每一梯次被學員當場戳破。
3. **「三個最常見的坑」第③條在這台機器不穩定重現**：PM 是「build 後第一次 dev 才 500，generate 後反而正常」，QA 是「不 500 但一堆快取告警」。教材用「會爆」的確定語氣不準確；但**兩人都證實解法有效**，所以要改的是語氣與觸發時機的描述，不是刪掉這一段。
4. **`pnpm generate` 在 Node 24 上開箱失敗（QA 遇到、需改 nuxt.config 才過）**。教材的 step0 preflight 只檢查 Node ≥ 20，沒有上限；範本鎖 Nuxt 3.21.1 是為了避開已知回歸，但 Nitro prerender 在新 Node 上的路徑解析問題不在檢查範圍。這是課後題的環境風險，值得在 README 補一句。
5. **第 10 項驗收「搜尋 `#` 開頭的色碼」寫法有陷阱**：全專案一定掃到 token 正本的 351 行。PM 說得很直白：「我一定會把 351 行當成作業失敗。」一句話就能修好的東西。
6. **兩位都把「一行 TODO 不等於 API 契約」講出來了**，而且 PM 講得更完整。教材那句「後端課要做的就是把那一行換成真的 API——而且頁面一行都不用改」是這門課銜接下一門課的賣點，**但它現在寫得像保證**。
7. **我要為這一步的簡化負責並記錄清楚**：沒有真的推上 GitHub，所以「發布到 GitHub Pages」的實際成功率、Pages 的 1～2 分鐘等待、以及坑①②在真實 Pages 上的表現，這次**沒有驗到**。兩位的紙上檢查品質很高，但那不能取代一次真實發布。**下一梯次若要驗這一段，必須先取得帳號授權。**
