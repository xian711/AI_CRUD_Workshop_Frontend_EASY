# SRS／設計文件 最小樣板（step3 用）

> **這份是「交出來要長什麼樣」的骨架，不是答案。**
> 起手 prompt 會叫 AI 先照這份的「釐清規矩」出選擇題，再照這份產出 SRS、設計文件、UML 圖和任務清單。
> 試教時發現一個問題：手冊只說「AI 會交出 SRS 和設計文件」，
> 沒說**檔名叫什麼、最少要有哪幾段、你要看什麼**——結果學員只能「有兩個檔就打勾」，
> 甚至有人根本沒交，因為任務清單是 AI 自己列的、沒人檢查。
>
> 所以這份把最低門檻定死：**SRS 四段、設計文件四段、圖四張，缺一樣就退回。**

---

## SDD 是什麼：規格驅動開發

**先給比喻：蓋房子要先畫設計圖。**

1. 屋主只會說「我要三房兩廳、採光好」。建築師要問：「主臥要不要衛浴？」「陽台要不要外推？」→ 你寫白話 PRD，**AI 找出沒講清楚的地方，用選擇題問你**。
2. 建築師畫圖，屋主**看圖點頭**才開工。屋主看平面圖就懂，不用看鋼筋計算書。→ **你看圖就好，不用看程式。**
3. 施工時改了隔間，竣工圖要跟著改。不改的話，下次裝修的人照舊圖打牆，會打到水管。→ **程式改了，文件跟著改。**

**再講技術：** 這門課的 SDD＝**規格驅動開發**（Specification-Driven Development），做法跟 SpecKit 一樣。流程六步：

1. **PRD**：業務單位用白話寫的需求（`PRD-中心裝備物資.md`）。一定不完整，這是正常的。旁邊還有資訊單位給的 `技術約定-中心裝備物資.md`（網址、欄位英文名、測試掛點）。
2. **AI 找缺口，用選擇題釐清，你拍板**：照下一節的「釐清規矩」。
3. **SRS**：拍板後的「要做什麼」定稿。
4. **設計文件＋圖**：「怎麼做」的紀錄，**圖為主**。
5. **任務清單**：拆成小到能單獨驗收的任務。
6. **寫程式**：你說「開工」，AI 才寫。

寫完程式之後，step4 的 LOOP 會再驗一次。**程式改了，文件跟著改**——這條規則從頭到尾都有效。

> 注意：有些書把 SDD 寫成 Software Design Document（軟體設計文件）。**本課的 SDD 只指上面這套流程**，
> 「怎麼做」的那份文件叫「設計文件」（檔名開頭 `DESIGN-`），免得兩個意思搞混。

**模型怎麼選：** 文件階段（步驟 2～5）用 **Opus 5.5** 想清楚。步驟 6 寫程式，換成 **Sonnet 5.5**。有 harness 和範本，寫程式不用最貴的模型。

## 釐清規矩：AI 怎麼出選擇題（給 AI 讀）

PRD 是不懂程式的人寫的，一定有缺口。**PRD 沒寫的，不准自己決定，要問。**

### 一定要檢查的缺口

讀完 PRD 和技術約定，逐項檢查下面這幾類。PRD 已經寫清楚的就不用問；沒寫、或寫得不清楚的，每一項出一題：

1. **編號怎麼編**：規則（例如 `PW-GEN-001`）、什麼時候產生、怎麼保證不重複、改了分類要不要換號。
2. **新增、查詢、修改、刪除四件事有沒有都講到**：刪除最常被漏掉。要不要刪、刪之前要不要確認。
3. **選項欄位的預設值**：下拉、單選新增時一律空白（harness `CLAUDE.md` 第 11 條）。哪個選項欄位新增時應該先帶值，PRD 沒寫就要問。
4. **聯絡方式**：要收哪些種類、要不要拆成幾欄、格式怎麼驗。
5. **日期**：能不能填未來的日期、過去的日期有沒有下限。
6. **要交出去的資料**：PRD 說要「交給別人」的，問格式（例如 CSV）、全部還是只有當頁。
7. **必填、上下限**：哪些一定要填、數字有沒有上限下限，PRD 沒講清楚的。
8. **跟技術約定衝突的地方**：例如要拆欄位，會讓欄位英文名跟技術約定不一樣。

### 題目怎麼寫

1. **用業務的話問，不用技術名詞。** 問「打錯了要不要能刪掉？」，不問「要不要實作 DELETE」。
2. 每題 2～4 個選項，**標出建議的那個，附一句理由**。
3. 能舉例就舉例。例如編碼規則，每個選項都寫一個實際的編號長什麼樣。
4. 一題只問一件事。
5. 拍板的結果，全部寫進 SRS 第 1 段。

## 給不會寫程式的人：這兩個縮寫是什麼

| 縮寫 | 中文 | 一句話 | 誰主要看 |
|---|---|---|---|
| **SRS** | 軟體需求規格書 | **「要做什麼」** 的定稿。PRD 是提需求，SRS 是拍板後的版本——含你答過的每一題。 | 你（驗收依據）、後端、QA |
| **DESIGN** | 設計文件 | **「怎麼做」** 的紀錄，**圖為主**。哪些檔複製改名、哪些直接共用、資料長什麼樣。圖另外放一個 HTML 檔，用瀏覽器開。 | 工程師、接手的人；你看圖就好 |

**你要看的其實只有兩樣：SRS 四段，加上設計文件的圖。** 裡面的技術細節你不用讀懂，
但**SRS 第 1 段和第 3 段一定要親自核**——那兩段是「範圍有沒有被偷改」的證據。

## 檔名約定

放在你的工作專案根目錄（跟 PRD 同一層）：

```
my-equipment-app/
├─ PRD-中心裝備物資.md          ← 題目：業務單位寫的白話需求
├─ 技術約定-中心裝備物資.md      ← 題目：資訊單位給的約定
├─ SRS-中心裝備物資.md          ← AI 產出（要做什麼）
├─ DESIGN-中心裝備物資.md       ← AI 產出（怎麼做）
└─ DIAGRAMS-中心裝備物資.html   ← AI 產出（圖，用瀏覽器開）
```

任務清單回在對話裡就好；想留檔可以存成 `TASKS.md`（參考解就是這樣做）。

## SRS 最小四段

### 1. 已拍板決策 ★必核

AI 問過的**每一題**都寫進來，**一題一列，含理由**。題數依 PRD 缺多少而定，不是固定幾題。

| # | 問題（白話） | 裁決 | 理由 | 誰拍板 |
|---|---|---|---|---|
| Q1 | （例：品項編碼怎麼編？） | （你的選擇） | （你的一句話理由） | （你的名字） |
| Q2 | （例：打錯了要不要能刪掉？） | | | |
| … | | | | |

**核什麼**：每一題都在嗎？裁決跟你當時選的一樣嗎？理由是你的話，還是 AI 幫你編的？

### 2. 需求追溯 ★必核

把 PRD 第 3 節的 12 項資料、第 5 節的 8 件事、第 7 節的 7 條驗收，對上「實際做出來的東西」。

| PRD 項目 | 有沒有做 | 做在哪 | 備註 |
|---|:---:|---|---|
| 第 3 節 12 項資料（逐項列） | ✅／✖ | 哪個檔 | 有差異就寫清楚 |
| 第 5 節 8 件事（逐條列） | ✅／✖ | 哪個畫面 | |
| 第 7 節 7 條驗收（逐條列） | ✅／✖ | 怎麼驗 | |

**核什麼**：有沒有**漏做**（PRD 有、表上沒有），有沒有**偷加**（表上有、PRD 沒有）。
偷加不一定是壞事，但**必須是你點頭的**，不是 AI 自己決定的。

### 3. 範圍外 ★必核

照抄 PRD 第 6 節，**再加上「這一輪決定不做」的東西**。

- （PRD 原本就列的範圍外項目）
- （你在釐清時砍掉的東西，寫明為什麼砍）

**核什麼**：這一段是你回公司時的擋箭牌。有人問「為什麼沒有借用歸還」，答案在這裡。

### 4. 待定與風險

正式上線前還缺什麼。試教時 PM／QA 常補的有：

- 後端集中儲存與 API 契約（現在是前端 mock）
- 權限與登入、操作稽核
- 軟刪除政策（現在是硬刪除）
- 匯出含個資的權限與遮罩
- 邊界規格未定：電話分機、排序 tie-breaker、數量上限、CSV 公式注入防護

## 設計文件最小四段

第 1～4 段寫在 `DESIGN-中心裝備物資.md`；第 5 段是圖，另外放 `DIAGRAMS-中心裝備物資.html`。

### 1. 檔案責任 ★可以核

| 檔案 | 處置 | 為什麼 |
|---|---|---|
| `pages/equipment/crud/index.vue` | 複製改名 | 跟實體長相有關 |
| `pages/equipment/crud/[id].vue` | 複製改名 | |
| `composables/useEquipmentItems.ts` | 複製改名 | |
| `components/equipment/EquipmentFormField.vue` | 複製改名 | 命名空間隔離 |
| `components/equipment/EquipmentStatusBadge.vue` | 複製改名 | |
| `composables/useTemplateListPage.ts` | **直接共用，未修改** | 通用機制 |
| `utils/templateValidation.ts` | **直接共用，未修改** | 通用機制 |
| `utils/templateCsv.ts` | **直接共用，未修改** | 通用機制 |

**核什麼**：就是手冊 step3「產出物：8 檔改名對照」那張表。
**特別核「直接共用」那三個**——它們應該與範本原檔**完全相同**（可以用檔案雜湊比一次）。
試教時有學員為了讓 E2E 變綠，把共用的列表工廠拆掉自己重寫一套，
共用檔本身沒被改，所以雜湊比對過了——**但心法已經破功**。所以這一段要順便寫「有沒有真的在用」。

### 2. 資料模型

- 型別定義（12 個欄位：英文名照技術約定、型別、必填）
- **欄位英文名就是未來後端 API 的介面**，照技術約定，不改
- 種子資料：幾筆、涵蓋哪些分類與狀態（對照技術約定第 4 節的五條約定）
- 品項編碼規則：你拍板的格式，以及怎麼保證不重複
- 選項欄位的預設值：哪些空白、哪些有預設（有預設的要寫是哪一題拍板的）

### 3. 關鍵決策的實作方式

拍板的每一題，凡是會影響程式的，一題一段，寫「怎麼做的」＋「為什麼不用別的做法」。通常包含：

- 編碼：什麼時候算、怎麼保證唯一
- 刪除：硬刪除還是軟刪除、確認彈窗用哪個元件
- 匯出：匯出全量還是當頁、編碼與 BOM 怎麼處理
- 預設值、電話格式、日期範圍：照拍板結果怎麼驗

### 4. 遵守 harness 的證據

| 規則 | 怎麼證明 |
|---|---|
| 禁止硬編碼色碼 | 新增檔搜尋 `#[0-9a-fA-F]{3,8}` 應為 0 命中 |
| 禁止硬編碼 px | 新增檔搜尋 `\d+px` 應為 0 命中（Tailwind 的 `px-3` 這類間距 class 不算，它走 token） |
| 禁止 `console.log` | 搜尋應為 0 命中 |
| 單檔行數 | 列表頁 ≤ 420、明細頁 ≤ 550、其餘 ≤ 500 |
| 下拉用「全部」哨兵 | 不用空字串當「全部」 |
| 選項欄位不預設 | 新增表單的下拉一律空白＋「請選擇○○」，只有拍板過的欄位有預設 |
| 日期欄用原生 date input | 沒有引入日曆套件 |

### 5. 圖（DIAGRAMS-中心裝備物資.html）★你看這段就好

**圖優先：用看圖取代看程式碼細節。圖要讓不懂資訊的人看得懂。**

至少四張 mermaid 圖：

| # | 圖 | 要看得出什麼 |
|---|---|---|
| ① | 用例圖：誰能做哪些事 | 管理人員能做的每一件事：查詢、新增、修改、刪除、匯出…… |
| ② | 零件圖：哪些照範本改名、哪些直接共用 | 5 個**照範本複製改名**、3 個**直接共用**（用顏色分開） |
| ③ | 資料圖：一筆裝備記哪些資料 | 12 項資料、哪些一定要填，以及分類、狀態這些固定選項 |
| ④ | 流程圖：新增一筆裝備 | 選分類 → 選項目 → 馬上算出編碼 → 儲存 → 檢查 → 存進清冊；檢查沒過怎麼辦 |

想多畫可以（例如狀態圖：正常、維修中、已報廢怎麼互換），但這四張一定要有。

**中文規矩（給不懂資訊的人看）：**

1. **圖上的字一律中文。** 程式檔名、欄位英文名、函式名不准單獨出現；真的要放，寫成「中文（英文）」，例如「數量（qty）」「列表頁（index.vue）」。
2. 流程圖的參與者寫**角色**，不寫檔名：例如「管理人員」「新增畫面」「檢查規則」「裝備清冊」。
3. 每張圖上方三樣東西：
   - **標題**：這是什麼圖。
   - **一句話**：這張圖在說什麼。
   - **怎麼看**：2～3 點，用白話講框、箭頭、顏色代表什麼。例如「箭頭從左到右是時間順序」「綠色框是照範本改名的」。
4. 每張圖下方一行 **「看完你要答得出來」**：一個問題，例如「管理人員能做哪幾件事？」。

**格式要求：**

1. 字級 22px 以上：mermaid init 寫 `%%{init: {'theme':'neutral','themeVariables':{'fontSize':'22px'}}}%%`。
2. 用瀏覽器打開就看得到圖，沒有紅字的 syntax error。
3. 可以照抄範本 `step2_speedrun_kit/2.1_sample_app/DIAGRAMS.html` 的 HTML 骨架、mermaid init 設定（mermaid@10、neutral 主題）和「怎麼看」的寫法。
4. 圖的內容要跟第 1～4 段一致：零件圖的「直接共用」三個檔，跟第 1 段那張表一樣。

**核什麼**：用瀏覽器打開，四張圖都出得來嗎？不看程式，你看得懂「誰能做什麼、檔案怎麼分、資料長什麼樣、新增怎麼跑」嗎？
看不懂就是圖畫得不好，退回去請 AI 重畫。想看畫好的樣子，參考解在 `step3_new_module/docs/DIAGRAMS-裝備物資.html`。

## step4 LOOP 之後：文件跟著程式改

step4 的 LOOP 會為了讓測試變綠而改程式（例如補 `data-testid`、改欄位驗證、改文案）。
**程式改了，SRS、設計文件、圖要同步更新**，否則三個月後的人照文件找，會找錯地方。

1. 改動的地方標「**step4 LOOP 後**」，例如：`（step4 LOOP 後）新增 4 個 data-testid 掛載點`。
2. 三個檔都要看：`SRS-中心裝備物資.md`、`DESIGN-中心裝備物資.md`、`DIAGRAMS-中心裝備物資.html`。
3. 這件事 AI 會照 `step4_loop_e2e/LOOP-規矩.md` 自己做；你驗收時只要確認有標記。

## 一句話收尾

**SRS 回答「這一版答應了什麼」，設計文件回答「怎麼做、動了哪些檔」，圖讓人不用讀程式就看懂。**
三份加起來，就是三個月後有人問「當初為什麼這樣做」時，你唯一拿得出來的東西。
