# SRS／SDD 最小樣板（step3 ④ 用）

> **這份是「交出來要長什麼樣」的骨架，不是答案。**
> 起手 prompt 的 T7 會叫 AI 生 SRS 與 SDD。試教時發現一個問題：手冊只說「AI 會交出 SRS／SDD」，
> 沒說**檔名叫什麼、最少要有哪幾段、你要看什麼**——結果學員只能「有兩個檔就打勾」，
> 甚至有人根本沒交，因為任務清單是 AI 自己列的、沒人檢查。
>
> 所以這份把最低門檻定死：**四段，缺一段就退回。**

---

## 給不會寫程式的人：這兩個縮寫是什麼

| 縮寫 | 中文 | 一句話 | 誰主要看 |
|---|---|---|---|
| **SRS** | 軟體需求規格書 | **「要做什麼」** 的定稿。PRD 是提需求，SRS 是拍板後的版本——含你的三題裁決。 | 你（驗收依據）、後端、QA |
| **SDD** | 軟體設計文件 | **「怎麼做」** 的紀錄。哪些檔複製改名、哪些直接共用、資料長什麼樣。 | 工程師、接手的人 |

**PM 要看的其實只有四件事**（就是下面四段）。裡面的技術細節你不用讀懂，
但**第 1 段和第 3 段一定要親自核**——那兩段是「範圍有沒有被偷改」的證據。

---

## 檔名約定

放在你的工作專案根目錄（跟 PRD 同一層）：

```
my-equipment-app/
├─ PRD-中心裝備物資.md      ← 題目（你收到的）
├─ SRS-中心裝備物資.md      ← AI 產出（要做什麼）
└─ SDD-中心裝備物資.md      ← AI 產出（怎麼做）
```

## SRS 最小四段

### 1. 已拍板決策 ★PM 必核

把 step3 ③ 的三題裁決寫進來，**一題一列，含理由**。

| # | 決策點 | 裁決 | 理由 | 誰拍板 |
|---|---|---|---|---|
| D1 | 品項要不要補刪除功能 | （你的選擇） | （你的一句話理由） | （你的名字） |
| D2 | 匯出做不做 | | | |
| D3 | 品項編碼規則 | | | |

**核什麼**：三題都在嗎？裁決跟你當時說的一樣嗎？理由是你的話，還是 AI 幫你編的？

### 2. 需求追溯 ★PM 必核

把 PRD 的 12 欄與 8 條驗收條件，對上「實際做出來的東西」。

| PRD 項目 | 有沒有做 | 做在哪 | 備註 |
|---|:---:|---|---|
| 2 節 12 欄（逐欄列） | ✅／✖ | 哪個檔 | 有差異就寫清楚 |
| 6 節 8 條驗收條件（逐條列） | ✅／✖ | 怎麼驗 | |

**核什麼**：有沒有**漏做**（PRD 有、表上沒有），有沒有**偷加**（表上有、PRD 沒有）。
偷加不一定是壞事，但**必須是你點頭的**，不是 AI 自己決定的。

### 3. 範圍外 ★PM 必核

照抄 PRD 第 7 節，**再加上「這一輪決定不做」的東西**。

- （PRD 原本就列的範圍外項目）
- （你在課堂上砍掉的東西，寫明為什麼砍）

**核什麼**：這一段是你回公司時的擋箭牌。有人問「為什麼沒有借用歸還」，答案在這裡。

### 4. 待定與風險

正式上線前還缺什麼。試教時 PM／QA 常補的有：

- 後端集中儲存與 API 契約（現在是前端 mock）
- 權限與登入、操作稽核
- 軟刪除政策（現在是硬刪除）
- 匯出含個資的權限與遮罩
- 邊界規格未定：電話分機、排序 tie-breaker、數量上限、CSV 公式注入防護

## SDD 最小四段

### 1. 檔案責任 ★PM 可以核

| 檔案 | 處置 | 為什麼 |
|---|---|---|
| `pages/equipment/crud/index.vue` | 複製改名 | 跟實體長相有關 |
| `pages/equipment/crud/[id].vue` | 複製改名 | |
| `composables/useEquipmentItems.ts` | 複製改名 | |
| `components/equipment/EquipmentFormField.vue` | 複製改名 | 命名空間隔離 |
| `components/equipment/EquipmentStatusBadge.vue` | 複製改名 | |
| `composables/useTemplateListPage.ts` | **直接共用，未修改** | 通用機制 |
| `utils/templateValidation.ts` | **直接共用，未修改** | 通用機制 |
| `utils/templateCsv.ts` | **直接共用，未修改** | 通用機制 |

**核什麼**：就是 step3 ⑦ 那張 8 檔對照表。
**特別核「直接共用」那三個**——它們應該與範本原檔**完全相同**（可以用檔案雜湊比一次）。
試教時有學員為了讓 E2E 變綠，把共用的列表工廠拆掉自己重寫一套，
共用檔本身沒被改，所以雜湊比對過了——**但心法已經破功**。所以這一段要順便寫「有沒有真的在用」。

### 2. 資料模型

- 型別定義（12 個欄位名、型別、必填）
- **欄位名就是未來後端 API 的介面**，現在定好不再改
- 種子資料：幾筆、涵蓋哪些分類與狀態（對照 PRD 2.1 節的五條約定）
- 品項編碼規則：你 D3 拍板的格式，以及怎麼保證不重複

### 3. 關鍵決策的實作方式

一個決策一段，寫「怎麼做的」＋「為什麼不用別的做法」。至少包含：

- 刪除（D1）：硬刪除還是軟刪除、確認彈窗用哪個元件
- 匯出（D2）：匯出全量還是當頁、編碼與 BOM 怎麼處理
- 編碼（D3）：什麼時候算、怎麼保證唯一

### 4. 遵守 harness 的證據

| 規則 | 怎麼證明 |
|---|---|
| 禁止硬編碼色碼／px | 新增檔搜尋 `#[0-9a-fA-F]{3,8}` 應為 0 命中 |
| 禁止 `console.log` | 搜尋應為 0 命中 |
| 單檔行數 | 列表頁 ≤ 420、明細頁 ≤ 550、其餘 ≤ 500 |
| 下拉用「全部」哨兵 | 不用空字串當「全部」 |
| 日期欄用原生 date input | 沒有引入日曆套件 |

## 一句話收尾

**SRS 回答「這一版到底答應了什麼」，SDD 回答「所以動了哪些檔」。**
兩份加起來，就是三個月後有人問「當初為什麼這樣做」時，你唯一拿得出來的東西。
