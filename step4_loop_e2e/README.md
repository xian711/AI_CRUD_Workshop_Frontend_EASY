# Step 4｜LOOP 工程 × E2E 驗證

> **這一步你只做兩件事：貼一個 prompt、驗收報告。**
> 「跑測試、看紅、判因、修、再跑」全部是 AI 的事——這就是 LOOP 工程。
> 紅燈不用刻意製造：你在 step3 用自己的 AI 模型生成的模組，本來就會跟驗收規格有落差，一跑 E2E 自然就紅。

---

## 一、LOOP 是什麼

一句話：**先給 AI 一個「可自動執行、會給出綠/紅」的驗證，再叫它自己修到綠。**

| 沒有 LOOP（人在迴圈裡） | 有 LOOP（AI 在迴圈裡） |
|--------------------------|--------------------------|
| AI 改一版 → 人手動開瀏覽器點一點 → 回報哪裡壞 → AI 再改 | AI 改一版 → 自己跑 E2E → 看到紅 → 自己修 → 再跑 → 綠了才停 |
| 人是瓶頸，改 5 次就累了 | 人只看最後結果，AI 跑幾輪都不喊累 |

**關鍵前提：要先有可自動執行的驗證。** 本資料夾已備好——`run-e2e.ps1`／`run-e2e.sh` 會開真瀏覽器跑 7 條 E2E 測試，exit 0＝全綠、exit 1＝有紅。沒有這個，LOOP 就退化成 AI 自說自話。

### 流程圖（一圈 LOOP 怎麼轉）

```
 你：貼 LOOP prompt（只貼這一次）
          │
          ▼
 ┌── AI 跑驗證 run-e2e ──► 全綠？ ──是──► AI 交報告 ──► 你驗收
 │        ▲                 │
 │        │                否（有紅）
 │        │                 ▼
 │        │           AI 判因（App 不符規格？環境？測試本身？）
 │        │                 │
 │        │                 ▼
 │        └────────── AI 修正，再跑
 │                          │
 └──────────────────────────┘
             │
             │ 同一問題連修 2 次仍紅
             ▼
      停損：AI 停下來回報，換人判斷
```

### 架構圖（誰呼叫誰）

```
┌────────────── 人（你）──────────────┐
│      出 1 個 prompt ＋ 驗收報告      │
└──────────────────┬──────────────────┘
                   ▼
┌────────────── AI Agent ─────────────┐    ┌── 第二個 AI（選配）──┐
│   跑驗證 → 判因 → 修 App → 寫報告    │◄───│ 對抗審查：抓假綠、    │
└──────────────────┬──────────────────┘    │ 鬆斷言、猜的 selector │
                   ▼ 呼叫                   └──────────────────────┘
┌──────────── 驗證 harness ───────────┐
│ run-e2e 腳本（紅綠燈，exit 0/1）     │
│  └─ Playwright 7 條測試              │
│      └─ Chromium 真瀏覽器            │
└──────────────────┬──────────────────┘
                   ▼ 實際點擊、斷言
┌────────────── 受測 App ─────────────┐
│  你的 my-equipment-app（port 3100）  │
└─────────────────────────────────────┘
```

## 二、LOOP 的優點與限制

| 優點 | 說明 |
|------|------|
| 省人機來回 | 人只出一個 prompt＋一次驗收；中間 N 輪紅綠都是 AI 自己跑 |
| 不喊累、可重複 | 跑 10 輪成本幾乎等於跑 1 輪；每輪判定標準完全一致 |
| 品質由驗證把關 | 過不過由紅綠燈說了算，不是由 AI 的自我感覺說了算 |
| 結果可追溯 | 每輪紅了什麼、修了什麼都留在報告裡，可回頭檢討 |

| 限制／風險 | 對策（本課的做法） |
|-----------|-------------------|
| AI 會作弊：放寬斷言、跳過測試讓燈變綠 | prompt 鐵律禁止動測試斷言；驗收時 `git diff` 抽查 e2e 資料夾 |
| AI 會鬼打牆：同一個坑愈修愈亂 | 兩次停損：同一問題連修 2 次仍紅就停下回報 |
| 驗證寫得爛＝假綠也全過 | 換第二個 AI 對抗審查測試本身（見第五節） |
| 沒有自動驗證的東西不適用 | 先寫驗證再開 LOOP；寫不出自動驗證的（如視覺美感）回歸人工審 |

## 三、主活動：把「你自己的模組」修到全綠

前提：你在 step3 生成的 `my-equipment-app` 還在 3100 跑著。
每個人用的 AI 模型不同、生成結果不同，跟驗收規格的落差就是天然的紅燈——**這 7 條 E2E 就是可執行的驗收規格**。

在**工作坊根目錄**開 AI Agent，整段貼上：

```
你是 LOOP 工程師，接下來自己跑完，中途不要問我。
受測 App：step3_new_module/my-equipment-app（我用 AI 生成的裝備物資模組）。
驗證指令（紅綠燈）：Windows 跑 powershell -ExecutionPolicy Bypass -File step4_loop_e2e/run-e2e.ps1；
macOS/Linux 跑 bash step4_loop_e2e/run-e2e.sh。exit 0＝全綠、exit 1＝有紅。

依序完成：
1. 確認 http://localhost:3100 跑的是受測 App；沒開就自己在背景啟動
   （cd step3_new_module/my-equipment-app 後 pnpm dev），等可連線再繼續；
   若 3100 被別的程式佔用，停下回報，等我處理。
2. 跑驗證。紅了就逐條判因，分三類處理：
   a. App 不符驗收規格（最常見）→ 修 my-equipment-app，遵守它根目錄的 harness 規則。
   b. 環境問題（server 沒起、相依沒裝）→ 修環境。
   c. 測試本身的問題 → 停下回報理由，等我裁決，不准自己改測試。
3. 修完再跑，直到 7 條全綠。

鐵律：
- 同一個問題連續修兩次還沒好，停下來回報，不要無限撞牆。
- 不准為了讓燈變綠去放寬測試斷言、跳過測試、或改測試預期條數。

完成後交報告：
- 每一輪：紅了哪幾條、一句話根因、修了哪個檔。
- 最後：全綠總結行（7 passed）。
```

> **一次就全綠？** 恭喜，代表你的模組已通過驗收規格，報告只有一輪、直接收工。
> 這也是正常結果之一——LOOP 的價值在「有紅時不用人跳進去」，不在硬要看到紅。

## 四、換你上場：驗收 AI 的報告

AI 說「做完了」不算數，照這張表核：

| 檢查點 | 怎麼核 |
|--------|--------|
| 每輪紀錄完整 | 紅了哪幾條、根因、修了哪個檔，一輪一列 |
| 根因說得通 | 是「App 不符規格」就該修 App；說「測試有問題」的要有你的裁決紀錄 |
| 測試沒被動過 | 在 `step4_loop_e2e/` 跑 `git diff e2e/`，應該是空的 |
| 最終真的綠 | 報告附 `7 passed`、exit 0 的總結行 |

## 五、進階：第二個 AI 對抗審查

寫測試（或修 App）的 AI 不適合審自己——它傾向相信自己做對了。開**另一個 AI**（例如本機 Codex），貼這段：

```
你的任務是「盡力推翻」step4_loop_e2e/e2e 這套 E2E 測試，不是誇獎它：
1. 有沒有「假綠」——斷言太鬆、選到隱藏節點、等到的是別的元素？
2. selector 是不是猜的？有沒有靠位置索引（nth）這種一改版就碎的寫法？
3. 測試之間會不會互相污染（前一條的資料影響後一條）？
逐條給「可被推翻的具體理由」，能重現就附步驟；找不到問題也要說明你怎麼確認的。
```

它挑出的問題交回原 AI 修 → 再跑 E2E → 再審。這就是「對抗式 LOOP」——本教材自己就被這樣審過一輪（見 [`ADVERSARIAL_REVIEW_R1.md`](ADVERSARIAL_REVIEW_R1.md)）。

## 六、七條測試在驗什麼

每條驗一個 CRUD 觀念，合起來就是這個模組的**可執行驗收規格**：

| 編號 | 驗什麼 | CRUD 觀念 |
|------|--------|----------|
| E1 | `/equipment/crud` 看得到表格、「共 24 筆」 | Read |
| E2 | 「發電機」縮到 2 筆、編碼「PW-GEN」也命中、清除後還原 | Filter |
| E3 | 新增：分類→項目連動 → 編碼預覽 `PW-GEN-003` → 儲存 → 共 25 筆 | Create |
| E4 | 空表單直接儲存 → 「請選擇分類」且停在表單頁 | Validation |
| E5 | 刪除 → 確認框 → 取消不變、確認後 -1 且該編碼消失 | Delete |
| E6 | `/template/crud` 正常載入（沒改壞範本） | Regression |
| E7 | 編輯：改數量與存放地點 → 儲存 → 回查新值生效 | Update |

> 這 7 條是**功能驗證＋失敗截圖診斷**（失敗自動存截圖，人和 AI 都能判讀），不是 pixel 比對的視覺回歸。測試資料是記憶體 mock，每次整頁載入重置回 24 筆種子，測試之間不互相污染。
