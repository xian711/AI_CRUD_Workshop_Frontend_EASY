# step5 — 課程總結與回去怎麼用

> 評量標準與提交格式見 [RUBRIC.md](RUBRIC.md)（六面向 100 分、70 分及格、需求裁切／CRUD 驗收／LOOP 三項不得為零）。

## 課程回顧

| Step | 帶走的觀念 |
|------|-----------|
| step1 為什麼要 harness | 同一句需求，有沒有附上「規矩」（harness）產出天差地遠——差的不是功能，是「像不像同一個團隊做出來的東西」。 |
| step2 CRUD 快速完工秘笈 | 一個成熟模組拆開來看，就是「範本（骨架）＋系統文件（SRS/SDD）＋前端 harness 四件（規矩）＋Design System（視覺語言）」四塊組合而成，缺一塊都會讓 AI 自由發揮出風險。 |
| step3 複製範本開發新模組 | 開發新模組的正確順序是 **PRD → 讓 AI 提「需求釐清選擇題」→ 生成 SRS/SDD → 生成程式與假資料 → 人工檢視反覆修正**；AI 主動提問＝起手 prompt 的 workflow 指令被遵守（不是 AI 卡住），而 harness 的效果是體現在生成的程式碼品質上（見 step1 A/B）。 |
| step4 加速技：LOOP 工程 | 不用每一步都盯著 AI：貼一個 prompt，讓它自己跑「改 → 驗 → 再改」把你的模組修到 E2E 全綠——紅燈不用刻意製造，不同 AI 模型生成的落差就是天然的紅；收尾一定要有人（或另一個 AI）驗收報告、雙 AI 對抗審查把關，不能只靠 AI 自己說「做完了」。 |

## 回去公司怎麼用

### ① 把前端 harness 四件帶進你的專案

把 `CLAUDE.md`、`CODE-RULES-ui-本專案.md`、`design-system-summary.md`、`使用說明-複製範本開發新模組.md` 四份文件複製到你專案的**根目錄**（sample-app 根目錄有現成一套），內容改成你們公司自己的規則（色票、命名慣例、驗證規則、禁止事項）。用 Codex 就再放一份 `AGENTS.md` 指向 CLAUDE.md。這是 AI 產出「像同一個團隊做的」的關鍵。

### ② 把既有的標準頁面整理成範本

挑一個你們平台裡最成熟、最多人抄過的 CRUD 頁面，拆成「複製區」（跟實體有關的型別、欄位、驗證）與「共用區」（跟實體無關的通用邏輯，例如列表狀態管理、CSV 匯出、驗證引擎）。可參考 `step2_speedrun_kit/2.1_sample_app/README.md` 的「8 個核心檔（複製改名 vs 直接共用）」對照表寫法。

### ③ 新需求走「PRD → 釐清選擇題 → SRS/SDD → 生成 → LOOP 驗證」流程

拿到新需求先寫一頁 PRD（可以很簡陋），丟給 AI 配上 harness 與範本；AI 該先回你「需求釐清選擇題」而不是直接動手；選完題目再讓它出 SRS/SDD 與程式；最後跑一輪 LOOP（改 → 驗 → 再改）＋人工或雙 AI 審查收尾。

## 常見問題

| 問題 | 回答 |
|------|------|
| 我們不是用 Nuxt，怎麼辦？ | harness 方法不綁框架。四件（CLAUDE.md / CODE-RULES / design 摘要 / 範本使用說明）換成你們的技術棧規則即可；範本拆分（複製區 vs 共用區）的心法在任何前端框架都適用。 |
| 我們沒有 Design System，怎麼辦？ | 不用一次到位。先從**色票**（品牌色、錯誤色、中性色）與**間距常數**（例如 4/8/16/24/40）開始定案，寫進 CODE-RULES，AI 就不會再亂配色、亂用魔術數字。元件規範可以之後再補。 |
| AI 生成的程式碼看起來很像，但細節怪怪的，怎麼辦？ | 這是正常現象，AI 生成永遠需要人工檢視。回頭檢查是不是 harness 規則沒寫清楚，或範本本身的「複製 vs 共用」邊界沒交代好；把發現的問題補進 CODE-RULES，下次就不會再錯。 |
| LOOP 工程會不會讓 AI 跑到失控？ | 每輪 LOOP 都要有明確的「驗」的標準（測試、E2E 檢查清單、視覺審查），沒有客觀驗收標準就不要放給 AI 自己跑。詳見 step4。 |

## 下一步：後端課預告
