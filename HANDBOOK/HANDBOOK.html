為什麼要有 harness？

🎯這一步要做到
  1. 用「同一句需求、只差有沒有附規矩」的兩個產出，親眼看出差別。
  2. 知道差別不在美醜，在「每個決定有沒有出處」。
  3. 知道 harness 管得住什麼、管不住什麼。
👀兩版差在哪

harness 就是你交給 AI 的一套「規矩」：專案規則（CODE-RULES）＋設計系統（色票、間距）＋標準範本。沒有它，AI 每次都會自己決定；有了它，AI 照你們的決定做。注意：現在的 AI 不給規矩也寫得出漂亮頁面——所以這一步不是在比誰好看。

下面兩張圖，是拿同一句需求、只差有沒有附規矩，各跑一次的產出。兩版都很好看，新增與刪除也都能用——這就是最重要的體會：左邊那版甚至可能比右邊更討喜（它自己配了色、加了圖示）。重點在別的地方：右邊每一個決定都有出處，左邊全是 AI 自己決定的。兩版核心功能相同，但欄位選項與驗證規則已經不一樣了（血型幾個選項、電話收不收 (02) 1234-5678），而這正是「這個決定是誰做的」的結果。

💡為什麼
把 harness 想成韁繩／馬具：不是限制馬跑，是讓馬跑得直。 馬（AI）的力氣一樣大，差別在有沒有方向。AI 越強，這件事越重要——因為它自己決定的東西會越來越合理、越來越好看，你越不容易發現它其實沒照你們的規矩走。一句話結論：同一句需求，差的不是 AI 的能力，是你有沒有把決定權拿回來。

② 當使用者玩一輪：CRUD 五個檢查點

逐一操作，確認每個都能重現（預期畫面見下面「你應該看到」）：新增一筆 → 進檢視頁編輯 → 刪除跳二次確認 → 關鍵字＋狀態篩選後複製網址開新分頁 → 匯出 CSV。

③ 看懂範本結構：8 個核心檔

打開 2.1_sample_app/README.md，對照裡面的「8 個核心檔（複製改名 vs 直接共用）」表看一遍。判斷準則只有一句：跟「這個實體長什麼樣子」有關的 → 複製改名；通用機制 → 直接共用。這張表就是 step3 你要叫 AI 照著做的事。

④ 認識規矩：規矩放在哪、誰會去讀

你不需要讀懂裡面的每一條規則——那是寫給 AI 讀的。就像滷茶葉蛋不必知道滷包裡有幾味藥材，但你得知道滷包放在哪、什麼時候丟下去、換鍋子的時候要不要一起帶走。這一步只要弄懂三件事。

「不用讀」講得更精準一點：不用逐條讀懂，不等於四份都不看。人至少要掃過 CLAUDE.md（48 行，知道底線在哪）；開新模組前要讀 使用說明-複製範本開發新模組.md（那份本來就是寫給人看的）；另外兩份由 AI 改碼時查、由人做 code review 時對照。
另外提醒：這個比喻只管「滷包放哪、要不要帶走」。它不負責回答「滷包裡的規矩對不對」——業務規則寫錯（例如「不能匯出個資」寫反了），AI 會照著做，錯得更快更整齊。規矩的內容要有人負責、有版本、有人審。
2.1_sample_app/sample-app/ ← 這一鍋就是範本專案 【滷包】給 AI 的規矩 — 4 份，不用逐條讀懂 ├─ CLAUDE.md 專案憲法：技術棧鎖定、鐵律精華 ├─ CODE-RULES-ui-本專案.md 前端規則細則：樣式／驗證／行數預算 ├─ design-system-summary.md 視覺 token 摘要：顏色與間距怎麼用 └─ 使用說明-複製範本開發新模組.md 操作手冊：哪些複製、哪些共用 （旁邊還有 AGENTS.md，是給部分 Agent 的入口便條，內容只寫「去讀 CLAUDE.md」） 【配方】範本程式 — AI 照著填的骨架，③ 對照過的 8 核心檔就在這裡 ├─ pages/ 列表頁、明細頁 ├─ components/ 欄位元件、狀態徽章、共用 App* 元件 ├─ composables/ 資料層、列表狀態工廠 └─ utils/ 驗證引擎、CSV 匯出 【不用管】設定檔 └─ package.json　nuxt.config.ts　tsconfig.json　app.config.ts …

鍋具怎麼用？答案是你幾乎什麼都不用做：

  1. 滷包不用你端上桌。不管你用哪一個 AI，規矩都會被讀到——有些 Agent 一開對話就自動讀根目錄的規則檔；不會自動讀的，step3 的起手 prompt 第一句就是「先依序讀完這四份文件再動作」。你不需要做任何設定。（哪個 Agent 屬於哪一種，見 step2_speedrun_kit/README.md 的對照表。）
  2. 滷包跟著鍋子走。step3 你會把整個 sample-app 複製成 my-equipment-app，這四份會一起被複製過去。新模組不必重新設定，直接繼承同一套規矩。
  3. 要改口味就改滷包本身。全教材只有這一份實檔，沒有第二份副本，改完立刻對 AI 生效。
想看一眼滷包裡有什麼？（選配）打開 CLAUDE.md 掃 30 秒就好——它只有 48 行，你會看到「鎖定技術棧不准換套件、禁止硬編碼顏色、危險操作要二次確認」這類鐵律。四份的完整分工與不同 AI Agent 的載入方式，見 step2_speedrun_kit/README.md 的「harness 四件：給 AI 的規矩」一節。

3

複製範本開發新模組重頭戲

🎯這一步要做到
  1. 讀懂 PRD，理解「PRD 給全貌，不是這堂課的範圍」。
  2. 把需求丟給 AI，讓它先出選擇題釐清範圍，你拍板。
  3. 打開瀏覽器驗收與修正，重現列表、表單、驗證、刪除、手機五件事。
👣跟著做

要長出的新模組是中心裝備物資（跑在 /equipment/crud），用的是跟 step2 同一套範本＋harness。

⓪ 準備工作區

動手之前，先把範本複製成自己的工作專案，並確認 AI Agent 的工作目錄就是這個專案根目錄（不然 AI 讀不到題目文件與 harness）。

$src = "step2_speedrun_kit\2.1_sample_app\sample-app"
$dst = "step3_new_module\my-equipment-app"
robocopy $src $dst /E /XD node_modules .nuxt .output | Out-Null

pnpm install
# 在「這個資料夾」開 AI Agent（工作目錄＝專案根目錄）

# ⚠ 同樣要排除 node_modules / .nuxt / .output（都會自動重建）
rsync -a --exclude node_modules --exclude .nuxt --exclude .output step2_speedrun_kit/2.1_sample_app/sample-app/ step3_new_module/my-equipment-app/
# 只把 PRD 放進專案（AI 才讀得到需求）

# 在「這個資料夾」開 AI Agent（工作目錄＝專案根目錄）

① 讀 PRD

打開 PRD-中心裝備物資.md。題目取材自真實災防平台的頁面（原系統 26 欄＋借用歸還＋維保提醒，課堂上絕對做不完），已先濃縮成一堂課做得完的課堂版（12 欄）——但刻意留了三個決策點（刪除補不補、匯出做不做、編碼規則簡不簡化）給你拍板，連「原系統沒有刪除功能」這種真實缺口都照實保留。

② 貼起手 prompt，讓 AI 先問問題

用 Agent 模式跟 AI 對話（它需要能自己讀檔、改檔）。整段複製貼上：

先依序讀完專案根目錄這四份，讀完再動作：CLAUDE.md、CODE-RULES-ui-本專案.md、

LOOP 工程 × E2E 驗證

🎯這一步要做到
  1. 說得出 LOOP 是什麼、優點與限制是什麼。
  2. 貼一個 prompt，讓 AI 把你自己在 step3 生成的模組修到 E2E 全綠。
  3. 驗收 AI 交回的報告，記住兩條鐵律：兩次停損、不准作弊。
📖LOOP 是什麼

一句話：先給 AI 一個「可自動執行、會給出綠/紅」的驗證，再叫它自己修到綠。

沒有 LOOP（人在迴圈裡）有 LOOP（AI 在迴圈裡）
AI 改一版 → 人手動開瀏覽器點一點 → 回報哪裡壞 → AI 再改AI 改一版 → 自己跑 E2E → 看到紅 → 自己修 → 再跑 → 綠了才停
人是瓶頸，改 5 次就累了人只看最後結果，AI 跑幾輪都不喊累

關鍵前提：要先有可自動執行的驗證（本課是 7 條 Playwright E2E，exit 0＝全綠、1＝有紅）。沒有這個，LOOP 就退化成 AI 自說自話。

流程圖（一圈 LOOP 怎麼轉）：

你：貼 LOOP prompt（只貼這一次） │ ▼ ┌── AI 跑驗證 run-e2e ──► 全綠？ ──是──► AI 交報告 ──► 你驗收 │ ▲ │ │ │ 否（有紅） │ │ ▼ │ │ AI 判因（App 不符規格？環境？測試本身？） │ │ │ │ │ ▼ │ └────────── AI 修正，再跑 │ │ └──────────────────────────┘ │ │ 同一問題連修 2 次仍紅 ▼ 停損：AI 停下來回報，換人判斷

架構圖（誰呼叫誰）：

┌────────────── 人（你）──────────────┐ │ 出 1 個 prompt ＋ 驗收報告 │ └──────────────────┬──────────────────┘ ▼ ┌────────────── AI Agent ─────────────┐ ┌── 第二個 AI（選配）──┐ │ 跑驗證 → 判因 → 修 App → 寫報告 │◄───│ 對抗審查：抓假綠、 │ └──────────────────┬──────────────────┘ │ 鬆斷言、猜的 selector │ ▼ 呼叫 └──────────────────────┘ ┌──────────── 驗證 harness ───────────┐ │ run-e2e 腳本（紅綠燈，exit 0/1） │ │ └─ Playwright 7 條測試 │ │ └─ Chromium 真瀏覽器 │ └──────────────────┬──────────────────┘ ▼ 實際點擊、斷言 ┌────────────── 受測 App ─────────────┐ │ 你的 my-equipment-app（port 3100） │ └─────────────────────────────────────┘

優點與限制：

優點說明
省人機來回人只出一個 prompt＋一次驗收，中間 N 輪紅綠都是 AI 自己跑
不喊累、可重複跑 10 輪成本幾乎等於 1 輪；每輪判定標準完全一致
品質由驗證把關過不過由紅綠燈說了算，不是 AI 的自我感覺
結果可追溯每輪紅了什麼、修了什麼都留在報告裡
限制／風險對策（本課做法）
AI 會作弊（放寬斷言、跳測試）prompt 鐵律禁止動測試；驗收時 git diff 抽查 e2e 資料夾
AI 會鬼打牆（愈修愈亂）兩次停損：同一問題連修 2 次仍紅就停下回報
驗證寫得爛＝假綠也全過換第二個 AI 對抗審查測試本身
沒有自動驗證的東西不適用先寫驗證再開 LOOP；驗不了的（如視覺美感）回歸人工審
👣跟著做

你只做兩件事：貼 prompt、驗收報告。 紅燈不用刻意製造——你在 step3 用自己的 AI 模型生成的 my-equipment-app，本來就會跟驗收規格有落差，一跑 E2E 自然就紅；這 7 條測試就是可執行的驗收規格。

- 同一個問題連續修兩次還沒好，停下來回報，不要無限撞牆。

  但要在報告裡標成「規格外調整」，並寫一句它跟 PRD 的差異在哪。
- 不准為了過測把「直接共用」的零件（useTemplateListPage / templateValidation /
  templateCsv / App*.vue）拆掉重寫一套；用不動就停下回報。

報告：每一輪紅了哪幾條、一句話根因、修了哪個檔；最後附全綠總結行（7 passed）。

腳本根本沒開始跑測試就掛了（Playwright 瀏覽器下載失敗、連不上 3100、PowerShell 擋住執行）環境問題，不是 LOOP 的活整段輸出貼給 AI 排除，同 step0 那一套

AI 自己停下來回報（觸發兩次停損）制度設計如此，代表該人介入了看它的根因說法：該修 App 就叫它修；它說「測試有問題」要你點頭才准動

🎯這一步要做到

👣跟著做

課程回顧：

Step帶走的觀念
step1同一句需求，有沒有附「規矩」（harness），產出天差地遠——差的不是功能，是像不像同一個團隊做的。
step2一個成熟模組＝範本（骨架）＋系統文件＋harness 四件＋Design System，缺一塊 AI 就會自由發揮出風險。
step3正確順序是 PRD → AI 提「釐清選擇題」→ 生成 SRS/SDD → 生成程式與假資料 → 人工反覆修正；AI 主動提問代表 harness 在運作。
step4可以讓 AI 自己跑「改→驗→再改」，但收尾一定要有人或另一個 AI 用 E2E 功能驗證＋失敗截圖診斷、對抗審查把關。

回去怎麼用（三步驟）：

  1. 把前端 harness 四件帶進你的專案——把 CLAUDE.md、CODE-RULES-ui-本專案.md、design-system-summary.md、使用說明-複製範本開發新模組.md 複製到你專案根目錄，內容改成你們公司的規則（色票、命名、驗證、禁止事項）。
  2. 把既有標準頁面整理成範本——挑一個最成熟的 CRUD 頁面，拆成「複製區」（跟實體有關的型別、欄位、驗證）與「共用區」（跟實體無關的通用邏輯）。
  3. 新需求走完整流程——PRD → 釐清選擇題 → SRS/SDD → 生成 → LOOP 驗證。拿到新需求先寫一頁 PRD（可以很簡陋），丟給 AI 配上 harness 與範本。

課後驗收題：一個人做一個問卷模組並發布上線，題目與步驟在 step6_survey/README.md。
